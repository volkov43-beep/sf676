# Формы СФ676 — клиентский контракт v1

Один `dialog`, пять сценариев, 13 ссылок с `data-request-form`. База: main `04bae08` (PR #8 объединён). Реализация использует принципы NeuroLab R03/R06/R12–R16: нативный диалог, восстановление фокуса, общую валидацию и отдельный будущий транспорт. Код другого проекта не переносился.

## Кнопки в характеристиках и приёмке

Обе ссылки открывают «Поможем подобрать комплектацию СФ676» (`configuration_help`). В черновике заявки сохраняются раздел и конкретная кнопка. После закрытия диалога фокус возвращается на исходную ссылку. При отключённом JavaScript ссылка ведёт к контактам в `#order`.

| Раздел | Кнопка | `sourceSection` | `sourceCta` |
| --- | --- | --- | --- |
| Основные характеристики | Проверить станок под мою деталь | `specs` | `specs-fit` |
| Приёмка и точность | Подобрать класс точности под мою задачу | `acceptance` | `acceptance-accuracy` |

## Запрос цены в конструкции, поставке и разделе завода

Три красные кнопки открывают «Получить цену СФ676 с доставкой» (`price_quote`). При открытии видны поля «Телефон или e-mail» и «Город доставки». Обязателен только контакт. В этих трёх сценариях открытия форма показывает обычный запрос цены без сводки платежей. Закрытие возвращает фокус на исходную кнопку. При отключённом JavaScript каждая ссылка ведёт к `#order`.

| Раздел | Кнопка | `sourceSection` | `sourceCta` |
| --- | --- | --- | --- |
| Конструкция | Узнать цену в нужной комплектации | `design` | `design-price` |
| Поставка и запуск | Рассчитать доставку до моего цеха | `delivery` | `delivery-quote` |
| Завод и карта поставок | Узнать цену для моего региона | `plant` | `plant-region` |

## Короткая форма цены

Описание формы — «Оставьте телефон или e-mail и укажите город доставки.» Под двумя основными полями находится нативный блок «Добавить детали». В нём можно указать имя, ИНН или название предприятия, адрес доставки и комментарий. Tab переводит фокус на заголовок блока, Enter или пробел переключает его. После раскрытия дополнительные поля доступны по Tab.

Сворачивание сохраняет введённые значения. Проверка учитывает все поля и раскрывает блок, если внутри обнаружена ошибка. Фокус получает первое ошибочное поле в блоке. При закрытии значения очищаются, при следующем открытии видны только контакт и город. Сводка из калькулятора отображается над основными полями. Формат `getDraft()` и ограничения полей приведены ниже.

## Открытие из будущего квиза / калькулятора

```js
const opened = window.SF676Requests?.open({
  formId: 'configuration_help',
  sourceSection: 'config',
  sourceCta: 'future-quiz',
  trigger: document.activeElement,
  context: {
    configuration: {
      workTable: '250 × 800 мм',
      spindleTaper: 'КМ4',
      droType: 'О',
      coordinates: 3,
      screwDrive: 'ШВП'
    }
  }
});
if (!opened) location.hash = 'order';
```

`open()` возвращает boolean; неизвестный сценарий и вложенное открытие отклоняются. `trigger` — элемент для возврата фокуса (по умолчанию текущий активный). Сначала `close()`, если нужно сменить сценарий; прежний ввод очищается. Без поддержки `dialog` API отсутствует, обычные `href="#order"` продолжают работать. Модифицированный клик по ссылке сохраняет стандартное поведение браузера.

Сценарии: `price_quote`, `configuration_help`, `repair_comparison`, `procurement_documents`, `procurement_nmck`. Идентификаторы CTA заданы в `data-source-cta`, раздел — в `data-source-section`; тексты кнопок не участвуют в маршрутизации.

`validate()` проверяет поля, показывает текстовые ошибки и фокусирует первую ошибку. Возвращает boolean. `getDraft()` по явному вызову возвращает новый объект только для открытой валидно заполненной формы, иначе `null`. Он ничего не отправляет и не сохраняет:

```js
{
  schemaVersion: 1,
  formId: 'price_quote',
  sourceSection: 'top',
  sourceCta: 'hero-price',
  context: {city: 'Тестовый город', deliveryAddress: '', comment: ''},
  contact: {value: 'qa@example.com', name: '', company: ''}
}
```

Во всех сценариях обязателен только `contact.value`. Он сохраняет исходный ввод, включая формат телефона. Необязательные текстовые поля открытой формы возвращаются строками, пустые — как `''`.

| Сценарий | Другие поля в `contact` | Поля в `context` |
|---|---|---|
| `price_quote` | `name`, `company` | `city`, `deliveryAddress`, `comment`. При переходе от калькулятора с рассчитанными платежами также `calculation` |
| `configuration_help` | `name`, `company` | `task`. Из мастера также передаётся `selector`. После квиза требования уже входят в сводку, поэтому `task` отсутствует |
| `repair_comparison` | `name` | `machineIdentity` — модель, изготовитель, заводской номер и год в одной строке или нескольких. `problem` — техническое состояние или неисправность |
| `procurement_documents` | `organization` | `purchaseType`, `documents` (массив ID запрошенных документов) |
| `procurement_nmck` | `organization` | `purchaseType`, `requirements`, `supplyCity`, `comment` |

`company` принимает ИНН или название предприятия свободным текстом. `deliveryAddress` принимает текст адреса без проверки по справочнику. Данные шильдика сохраняют введённый текст целиком. Прежние отдельные ключи `model` и `condition` в черновике ремонта отсутствуют.

Входной `context.configuration` принимает пять показанных ключей: строка ≤160 символов, конечное число либо boolean. HTML и неизвестные ключи не принимаются. Не передавать туда контакты. `context.selector` описан ниже. Начиная с итерации 08 резервная группа `calculation` принимает только проверяемую модель `payment_schedule` версии 1: RUB, user_input, целые копейки и illustrativeOnly: true. Общая форма сверяет арифметику заново; неизвестные поля, подменённые платежи и использование расчёта вне price_quote отклоняют open(). Контракт: [payment-calculator.md](payment-calculator.md). Это клиентская проверка; серверная схема потребуется перед приёмом заявок.

`sourceSection/sourceCta` — 1–80 латинских букв, цифр, `_` или `-`. Незаданные/некорректные значения получают `unknown/programmatic`. API не создаёт глобальной шины событий, логов или подписок на данные.

## Валидация и демонстрационный режим

- Контакт — до 254 символов, имя — до 100, предприятие или организация — до 200, город — до 160, адрес доставки — до 300, данные станка — до 500. Для задачи, состояния или неисправности, требований и комментария предел составляет 2000 символов. Ограничения проверяются и при программном вводе сверх `maxlength`.
- E-mail: базовая проверка структуры `local@domain.tld`, пробелов, пустых частей/точек и имени домена; допускаются `+`, поддомены и Unicode. Существование ящика не проверяется.
- Телефон: 10 цифр; 11 цифр с 7/8; международный с `+`, 7–15 цифр и ненулевой первой цифрой. Допускаются пробелы, скобки, точки, дефисы. Повтор одной цифры и несбалансированные скобки отклоняются. Маски, скрытой нормализации и обрезания номера нет. Это синтаксическая проверка, не проверка существования номера.
- HTML и управляющие символы отклоняются. Пользовательский ввод не вставляется через `innerHTML`.
- `Проверить заполнение` — отдельное действие. Оно никогда не означает приём обращения. Будущая отправка — отключённая кнопка; транспорт, endpoint, mock-success, CRM и аналитика отсутствуют.
- `form method="dialog"` исключает нативную сетевую отправку; submit также перехвачен. Согласие отключено и честно объяснено, ссылки на несуществующую политику нет.
- Все введённые значения/выборы и входной контекст удаляются при любом закрытии и `pagehide`. Нет local/sessionStorage, URL-параметров с контактами или console-логов. Объект, явно полученный будущим вызывающим кодом через `getDraft()`, находится под ответственностью этого кода; хранить или отправлять его в текущей итерации нельзя.
- Перед реальным приёмом нужны отдельные серверная валидация/схема, юридические документы, согласие и подтверждённый транспорт. Клиентская проверка их не заменяет.

При подключении приёма обращений завод согласует обязательность технических сведений для ремонта, необходимость загрузки фото шильдика и действие кнопки «Проверить заполнение». Для вложений потребуются серверная проверка типа и размера, обработка отклонённых файлов, безопасное хранение и передача ссылки или вложения в CRM.

## Повторение проверок

`python tests/verify-preservation.py <index.html из базовой main> index.html` — сохранение контента, таблиц, фото, SVG, старых скриптов и стилей.

Открыть `tests/request-forms.html` через локальное HTTP-превью. «Проверить матрицу» проверяет все 13 CTA при 320/375/390/768/1024/1366/1920 px в обычном режиме и при тексте 200%, очистку, контекст, геометрию, отсутствие транспортных/storage-вызовов; отдельно review/no-JS. «Проверить валидацию / API» проверяет отрицательные/положительные форматы, длины, HTML, контекст, выбор нескольких документов, безопасный submit и повторные открытия. Стенд использует только синтетические данные и не входит в рабочую страницу. Клавиши, указатель, видимый фокус и визуальную композицию дополнительно проверять вручную. Эмуляция высоты не заменяет реальную экранную клавиатуру.

Итерация 07 добавляет `context.selector` — строго проверяемый результат мастера (`exact` или `quiz`, schemaVersion 1). Сводка видна в общей форме `configuration_help` и сохраняется в снимке `getDraft()`. Для квиза поле `task` не повторяется. Контракт и проверки: [selector.md](selector.md). Остальные сценарии и правила демонстрационного режима сохранены.

Итерация 08: CTA `payment-calculator` передаёт фактический расчёт через `SF676Payments.getCalculation()`. При пустом/некорректном поле открывается стандартный price_quote без calculation. Сводка обозначает цену как пользовательскую и не подтверждённую заводом; getDraft() возвращает её в context.calculation. Остальные CTA и context.selector сохранены.
